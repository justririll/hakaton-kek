# Алгоритмы проекта и происхождение данных

Документ описывает код ветки `master` на коммите `cd88998`. Он дополняет [README.md](README.md); объяснение без технической подготовки — в [README_DAYN.MD](README_DAYN.MD). Если формулировка исходного README расходится с реализацией, ниже указано фактическое поведение кода.

## 1. Единственный контур проекта

| Контур | Источник | Что выполняется |
|---|---|---|
| `backend/` → `/api/*` → `frontend-ml/` | Только Excel-отчёты из `DATASET/` | Полный аналитический конвейер, описанный ниже |

Раньше контуров было три, и два из них выдавали заранее записанные числа:
прототип `app/` с заглушкой `/api/v1/analytics/dashboard` вместе с работавшим
с ним `frontend/`, а также `clusterization/cluster.py` с единственной строкой
`print("Eshkere")`. Все три удалены — вместе с фигурировавшими там значениями
заглушки (`K-Means (k=4)`, силуэт 0,64, переносы слотов, прирост посещаемости);
реального оптимизатора расписания за ними не стояло.

Рабочая кластеризация находится в `backend/app/ml/clustering.py`. Значения на
витрине приходят из API: захардкоженных в интерфейсе показателей больше нет —
см. [README_AUDIT.MD](README_AUDIT.MD).

## 2. Общая цепочка данных

```text
DATASET/*.xls, *.xlsx
  → excel_parser: чтение листов и показателей
  → dataset: единицы, пропуски, проверки, итоговые таблицы
  → features: 11 признаков + профиль в натуральных единицах
  → StandardScaler → PCA → выбор k → KMeans
                                      ↘ Ward и GMM для сравнения
  → forecast: план и линейный прогноз
  → recommender: правила и ранжирование рекомендаций
  → anomalies: логические проверки, MAD, Isolation Forest
  → validation: перестановки, исключение центров, устойчивость рекомендаций
  → объект Analytics в памяти → HTTP API → графики
```

Оркестратор — [pipeline.py](backend/app/ml/pipeline.py), функция `build_analytics`. В [main.py](backend/app/main.py) конвейер запускается при старте приложения. `POST /api/reload` повторяет расчёт из файлов. Между запросами хранится готовый объект в памяти процесса; отдельного постоянного хранилища моделей нет.

Модели обучаются на текущей сети центров без учителя: правильные классы заранее не размечены. Разделения на обучающую и тестовую выборки для оценки будущих прогнозов нет. Проверки устойчивости описаны отдельно ниже.

В схеме **26 исходных показателей**. В `facts` добавляются две суммы, поэтому таблица содержит **28 столбцов показателей**:

audience_total = trained_modules + trained_masterclasses + trained_cpd + trained_retraining

## 4. Разбор Excel и подготовка таблиц

### Чтение и распознавание

Код: [excel_parser.py](backend/app/ingest/excel_parser.py), `parse_directory`, `parse_report`, `_parse_indicator_sheet`.

1. Берутся `.xls` и `.xlsx` непосредственно из каталога, без рекурсивного обхода. Временные файлы `~$...` пропускаются; порядок файлов сортируется.
2. `.xls` читает `xlrd`, `.xlsx` — `openpyxl` в режиме `data_only=True`. Для формул используются сохранённые Excel результаты, сами формулы Python не пересчитывает.
3. Роль листа определяется по названию: титул, Форма 1, приложение, Форма 2.
4. Среди первых 15 строк ищется заголовок с «Наименование». Колонки базы 2025 года, факта 2026 года и плана распознаются по текстовым шаблонам.
5. Показатель связывается со схемой по паре «форма + номер строки». Название сверяется по ключевым словам; несовпадение создаёт предупреждение, но не отменяет чтение распознанной строки.
6. Пробелы в числах убираются, десятичная запятая заменяется точкой. Нераспознанное значение становится `None`.

Организация извлекается из титула; `org_id` строится из имени файла, короткое имя — из словаря или имени файла. Переименование файла может изменить идентификатор центра.

Повреждённая книга пропускается с записью ошибки в лог. Если не удалось прочитать ни одной книги, сборка завершается ошибкой. Пропущенная книга не обязательно попадает в список `QualityIssue`, поэтому число прочитанных организаций тоже нужно контролировать.

### Нормализация и контроль качества

Код: [dataset.py](backend/app/ingest/dataset.py).

- **Деньги:** для строки с подписью «тыс. рублей» пробуется умножение на 1000. Если результат больше 50 медиан ненулевых значений организаций без такой подписи, число оставляется без умножения и создаётся предупреждение. Это эвристика проверки единиц, а не доказательство ошибки автора отчёта. Применяется к фактам и базе прошлого года; для базы записи в отчёт не дублируются.
- **Суммы:** проверяются продукты, интеллектуальная собственность и услуги. Допустимое расхождение — `max(1, abs(итог) × 0.01)`. При превышении создаётся предупреждение, заявленный итог не заменяется суммой подпунктов.
- **Пропуски:** после проверки сумм отсутствующие фактические значения заполняются нулями с записью `imputed_zero`. База прошлого года целиком так не заполняется.
- **Производные суммы:** затем добавляются аудитория и предложение; для базы также рассчитывается `supply_total`.

Выход: `organizations`, `facts`, `baselines`, `plan_shares`, `issues`. Заполненность 100 % после заполнения нулями не означает, что все исходные ячейки были заполнены.

## 5. Признаки: как центр превращается в набор чисел

Код: [features.py](backend/app/ml/features.py), `build_features`, `build_profile_table`.

Обозначения: `A` — аудитория, `S` — предложение, `R` — резиденты, `P` — продукты, `V` — объём услуг, `M` — публикации, `F` — федеральные мероприятия. Все берутся из подготовленной `facts`.

`safe_ratio(x, y)` возвращает `x/y`, а при нулевом знаменателе — 0. `clip(x, a, b)` ограничивает число интервалом `[a, b]`. `log1p(x) = ln(1+x)` сжимает разницу между очень крупными и небольшими значениями.

| Признак модели | Расчёт |
|---|---|
| `clr_modules`, `clr_masterclasses`, `clr_cpd`, `clr_retraining` | CLR долей аудитории четырёх форматов |
| `log_audience` | `log1p(A)` |
| `log_supply` | `log1p(S)` |
| `audience_per_format` | `log1p(safe_ratio(A, S))` |
| `resident_rate` | `clip(safe_ratio(R, A), 0, 3)` |
| `product_rate` | `clip(safe_ratio(P, A), 0, 5)` |
| `revenue_per_participant` | `log1p(safe_ratio(V, A))` |
| `publicity_per_format` | `log1p(safe_ratio(M + F, S))` |

Итого 11 признаков. Отдельная таблица `profile` сохраняет интерпретируемые отношения без логарифмов и указанных ограничений: её используют рекомендации, карточки и одномерные аномалии. Одинаковое имя столбца в `features.matrix` и `profile` может означать разные шкалы.

### CLR: сравнение состава аудитории

Доли четырёх форматов складываются в 1. CLR сравнивает их относительные пропорции через логарифмы, чтобы работать с составом аудитории.

В `clr_transform` нули заменяются на `0.5 / 4 = 0.125`, то есть **12,5 %**. Положительные доли умножаются на `1 − 0.125 × количество_нулей`, затем строка нормируется к сумме 1. Если все доли нулевые, берётся `[0.25, 0.25, 0.25, 0.25]`.

```text
clr_j = ln(скорректированная_доля_j) − среднее(ln всех скорректированных долей)
```

Положительное значение означает перевес формата относительно среднего геометрического долей этого центра. Замена нулей здесь фиксированная и довольно заметная; она не подбирается по минимальному наблюдаемому числу, несмотря на формулировки комментариев и README.

## 6. StandardScaler и PCA

Код: [clustering.py](backend/app/ml/clustering.py), `_prepare`.

**StandardScaler** обучается на 11 признаках всей сети. Для каждого столбца вычитает среднее и делит на стандартное отклонение (`ddof=0`), чтобы рубли и доли не сравнивались в исходных несоизмеримых шкалах. Постоянный столбец после центрирования становится нулевым.

**PCA, метод главных компонент**, находит новые взаимно перпендикулярные направления, в которых различия между центрами выражены сильнее всего. Это линейные комбинации стандартизованных признаков.

Сначала оценивается полная PCA. Затем выбирается минимальное число компонент, сохраняющее не менее 85 % суммарной дисперсии; код ограничивает число снизу двумя, сверху числом признаков и `n−1`. PCA с выбранным числом компонент обучается заново.

Выходы: `feature_z` — стандартизованные признаки; `embedding` — координаты `pc1`, `pc2`, …; `loadings` — коэффициенты компонент; `explained_variance` — доли объяснённой дисперсии. На двумерной карте видны только `pc1` и `pc2`, а кластеризация использует все выбранные компоненты.

## 7. Три метода кластеризации

Все три получают **одну и ту же матрицу PCA**, число групп `k` и возвращают метку группы для каждого центра. Реализация — `_fit_labels` в [clustering.py](backend/app/ml/clustering.py).

| Метод | Принцип | Параметры и роль |
|---|---|---|
| KMeans | Назначает точки ближайшему центру группы, пересчитывает центры как средние и повторяет до сходимости. Минимизирует сумму квадратов расстояний внутри групп. | Основной метод конвейера; `n_init=25`, `random_state=42` |
| Ward | Начинает с отдельных точек и последовательно объединяет группы с минимальным увеличением внутригруппового разброса, пока не останется `k`. | `AgglomerativeClustering(linkage="ward")`; сравнение с KMeans |
| Gaussian Mixture, GMM | Представляет данные смесью нормальных распределений. EM попеременно оценивает принадлежности точек и параметры распределений. | `covariance_type="diag"`, `n_init=10`, `random_state=42`; `fit_predict` выдаёт итоговые жёсткие метки |

В обычном `build_analytics` выбран KMeans. Ward и GMM не голосуют за окончательную метку — они нужны для проверки согласия. Через Python-функцию `run_clustering` можно задать другой метод или `k`; HTTP-параметра переключения модели нет.

Для дендрограммы отдельно вызываются SciPy `linkage(method="ward")` и `dendrogram(no_plot=True)`. На входе та же PCA-матрица, на выходе координаты дерева и высоты слияний для визуализации.

### Выбор числа групп

Функции `k_range`, `evaluate_k`, `select_k`:

1. Верхняя граница диапазона — `max(2, min(6, n // 4))`; проверяются целые `k` начиная с 2. Для 20 центров это 2–5.
2. Пропускаются `k >= n`, решения с менее чем двумя полученными группами и кластером меньше двух объектов.
3. Для каждого оставшегося решения считаются метрики из таблицы ниже.
4. Каждая метрика нормируется min–max внутри кандидатов; постоянная метрика получает 0,5. Для DB направление разворачивается.
5. Считается сводная оценка. Из вариантов не хуже `лучшая_оценка − 0.05` выбирается наименьшее `k` — предпочтение более простого разбиения.

```text
score = 0.30 × силуэт + 0.30 × устойчивость
      + 0.15 × CH + 0.15 × обратный_DB + 0.10 × баланс
```

| Метрика | Что измеряет |
|---|---|
| Силуэт | Для точки `a` — средняя дистанция до своей группы, `b` — наименьшая средняя дистанция до другой. `(b−a)/max(a,b)`: ближе к 1 — хорошее разделение, около 0 — граница, отрицательное — возможна другая группа. Итог — среднее по точкам. |
| Calinski–Harabasz, CH | Отношение межгруппового и внутригруппового разброса с поправкой на `n` и `k`; больше лучше. |
| Davies–Bouldin, DB | Для каждой группы ищет наиболее похожую другую по отношению внутреннего разброса к расстоянию центров; среднее этих отношений должно быть меньше. |
| Баланс | Размер минимального кластера / размер максимального. |
| ARI | Согласие двух разбиений по парам объектов с поправкой на случайное совпадение. 1 — одинаково, около 0 — уровень случайного согласия; может быть отрицательным. Номера кластеров не обязаны совпадать. |

### Устойчивость при выборе k

`_stability` делает 200 раундов. В каждом независимо выбираются две подвыборки **без возвращения**, размером `max(k+1, round(0.8n))`. Они кластеризуются, после чего на общих объектах считается ARI. Раунды с пересечением меньше `k+1` или ошибкой разбиения пропускаются. Итог — средний ARI, либо 0 при отсутствии подходящих раундов.

Внутри этих проверок `n_init=3`. В коде процедура названа bootstrap, но фактически это повторное подвыборочное сравнение без возвращения, а не классический бутстрэп с повторяющимися наблюдениями. Масштабирование и PCA здесь уже зафиксированы на всей сети.

### Номера, названия и согласие

Группы перенумеровываются по убыванию размера. Для описания берётся среднее каждого **стандартизованного исходного признака**, выбираются три самых больших абсолютных отклонения от нуля и переводятся в словесные признаки. Имя выбирается из словаря с исключением уже занятых названий; это шаблонная логика, не генерация нейросетью.

Затем все три алгоритма запускаются с выбранным `k`, и для каждой пары рассчитывается ARI. Совпадение методов — дополнительное свидетельство устойчивости, но не доказательство наличия объективно «правильных» классов.

## 8. Проверки кластеризации и рекомендаций

Код: [validation.py](backend/app/ml/validation.py).

### Перестановочный тест

`permutation_test` получает PCA-координаты и итоговые метки. Метки перемешиваются 2000 раз, сохраняя размеры групп. Для каждого перемешивания считается силуэт.

```text
p = (число случайных силуэтов ≥ наблюдаемого + 1) / 2001
effect_size = (наблюдаемый силуэт − средний случайный) / std(случайных)
```

Данные не перемешиваются, модели на перестановках заново не подбираются. Поэтому тест сравнивает найденное разбиение со случайными метками на фиксированных данных, а не повторяет весь поиск лучшего `k` на случайных датасетах. Малое `p` не является вероятностью того, что кластеры «истинны».

### Leave-one-out и совместное попадание

`leave_one_out` строит представление всей сети, затем по очереди исключает один центр. Остальные заново кластеризуются с тем же `k`; ARI сравнивает новое разбиение с полным на оставшихся объектах.

Scaler, признаки и PCA внутри каждого исключения **не переобучаются**. Поэтому это проверка состава групп в фиксированном пространстве, а не полная проверка всего конвейера на независимых данных.

Для каждой пары центров считается частота совместного попадания в кластер среди прогонов, где оба присутствовали. `membership_confidence` — средняя такая частота по соседям из исходной группы. Центр помечается спорным при значении меньше 0,6. Это показатель стабильности, не вероятность правильного класса.

Вердикт кода: при `p >= 0.05` — структура неотличима от случайной; иначе при среднем ARI ≥ 0,75 — устойчивая, ≥ 0,5 — подвижные границы, ниже — только навигация. Это текстовый вердикт: сам API автоматически не блокирует выдачу кластеров.

### Устойчивость рекомендаций

`validate_recommendations` также исключает центры, повторно кластеризует оставшихся и запускает правила. Рекомендации сопоставляются по ключу `(org_id, rec_type, channel)`. Проверяется наличие рекомендации, а не совпадение эффекта, доверия и приоритета.

Для рекомендации исключённого центра прогон автоматически засчитывается как сохранение. Доля сохранений делится на общее число прогонов. Устойчивой считается рекомендация, сохранившаяся минимум в 80 % прогонов; `stable_share` — доля таких рекомендаций.

Есть ограничение реализации: в правила передаются полные `profile` и `facts`. При расширении эталона до сети исключённый центр может снова попасть в сравнение. Поэтому это не строгое исключение его данных из всех эталонов. Подготовка PCA также остаётся общей.

## 9. План и линейный прогноз

Код: [forecast.py](backend/app/ml/forecast.py), `build_plan_status`, `_plan_share`, `_status`.

Входы — `facts`, `baselines`, `plan_shares`. База `B` берётся из положительной суммы `dev_*` за 2025 год; если её нет, используется база строки 1 Формы 1. Прирост `g` читается из планового столбца этой строки: значения больше 1 делятся на 100, отсутствующее значение заменяется на 0,10.

Текущий факт `S` — сумма разработанных форматов из приложения, а не фактическая колонка `events_growth_rate`. Переменная `growth`, прочитанная из этой колонки, в последующих формулах не используется.

```text
цель T                 = B × (1 + g)
выполнение             = S / T
текущий месячный темп   = S / 9
прогноз года           = S × 12 / 9
разрыв прогноза         = прогноз − T
осталось сделать       = max(0, T − S)
требуемый темп          = осталось сделать / 3
```

Период 9 месяцев и длина года 12 месяцев заданы константами, не вычисляются из даты книги. Цель и остаток могут быть дробными: автоматического округления числа мероприятий вверх нет. При нулевой цели выполнение становится 1, если факт положительный, иначе 0.

| Условие | Статус |
|---|---|
| Нет положительной базы `B` | `без базы` |
| Прогноз / цель ≥ 1,10 | `опережение` |
| ≥ 1,00 и < 1,10 | `в графике` |
| ≥ 0,85 и < 1,00 | `риск` |
| < 0,85 | `срыв` |

Статус основан на **прогнозе к цели**, а не непосредственно на текущем выполнении. Это арифметическая экстраполяция, без обучения временной модели, сезонности и доверительного интервала. Название «нижняя оценка» из README не означает математической гарантии: фактический результат может оказаться и ниже прогноза.

## 10. Рекомендательная система

Код: [recommender.py](backend/app/ml/recommender.py). Входы: факты, профиль в натуральных единицах, метки кластеров, план и названия организаций. Это система правил и сравнений, а не LLM, коллаборативная фильтрация или обученная модель реакции на мероприятия.

### Эталон и доверие

`peer_stat` исключает сам центр и берёт других членов его кластера. Если соседей меньше трёх, берётся вся доступная сеть без этого центра. Считаются медиана, 25-й и 75-й процентили, лучший результат и размер группы. Медиана — центральное значение упорядоченного ряда; межквартильный размах `IQR = p75−p25` описывает разброс центральной половины.

```text
dispersion = IQR / median          (при median ≤ 0 используется 1)
penalty = 1 для кластера, 0.75 для сети
confidence = clip(n/(n+2) × 1/(1+dispersion) × penalty, 0.15, 0.95)
```

Это эвристическая оценка надёжности эталона. Для запуска нового формата результат дополнительно умножается на 0,8 и может стать ниже 0,15. Для риска плана доверие фиксировано: 0,9.

### Все семь правил

Здесь `fill` — обученные в конкретном формате / количество разработанных форматов этого вида. Для нулевого предложения наполняемость соседей считается нулевой. Эталоны не ограничены только центрами с ненулевой деятельностью.

| Правило | Когда срабатывает | Оценка эффекта |
|---|---|---|
| `launch_format` | Своё предложение равно 0; минимум 60 % других членов исходного кластера ведут формат; медианная наполняемость положительна | Один пилот × медианная наполняемость |
| `fix_format` | Формат есть, `p25 > 0`, своя наполняемость ниже `p25`, прибавка > 0,5 участника | `(median_fill − own_fill) × own_supply` |
| `expand_format` | Своя наполняемость не ниже положительной медианы; **доля аудитории** этого формата ниже медианной доли | `max(1, round(own_supply × 0.25)) × own_fill` |
| `raise_conversion` | Аудитория положительная и расчётная прибавка продуктов ≥ 1 | `(median_product_rate − own_product_rate) × A` |
| `monetize` | Аудитория положительная и прибавка объёма услуг ≥ 10 000 ₽ | `(median_revenue_per_participant − own_rate) × A`; эффект округляется до сотен рублей |
| `amplify_visibility` | Аудитория и предложение положительны, прибавка ≥ 3 | `(median_publicity_per_format − own_rate) × S`; округление до целого |
| `plan_risk` | Статус `риск` или `срыв`, положительный остаток до цели | `required_remaining`, то есть цель минус уже сделанный факт, а не цель минус прогноз |

Правила запуска, исправления и расширения проверяются по каждому из четырёх форматов. После ветки отсутствующего формата и после ветки низкой наполняемости обработка этого формата заканчивается через `continue`.

Для `launch_format` доля центров, ведущих формат, берётся из исходного кластера, даже если статистика наполняемости расширена до сети. Для `expand_format` используется доля **аудитории**, хотя в README встречается формулировка «доля линейки».

Публичность включает `media_publications + federal_events`, хотя эффект подписан как публикации. Соотношение продуктов и аудитории также не является долей людей, завершивших обучение: числа относятся к разным сущностям.

### Ранжирование

```text
normalized = clip(gain / max(abs(reference), 1e-9), 0, 2) / 2
raw_score  = normalized × confidence × type_weight
priority   = clip(round(rank(raw_score, pct=True) × 100), 1, 100)
```

`reference`: для правил форматов — вся аудитория центра; для продуктов — число продуктов; для денег — объём услуг; для публичности — только число публикаций; для плана — годовая цель. Таким образом оценивается относительный размер возможного улучшения.

| Тип | Вес |
|---|---:|
| `fix_format` | 1,00 |
| `plan_risk` | 0,95 |
| `expand_format` | 0,90 |
| `raise_conversion` | 0,85 |
| `monetize` | 0,70 |
| `amplify_visibility` | 0,60 |
| `launch_format` | 0,55 |

Веса задаются авторами, не обучаются. При равных сырых оценках pandas использует средний ранг. Приоритет — положение среди рекомендаций, не процент роста и не вероятность успеха.

Выход содержит действие, тип, формат, эффект, доверие, приоритет, объяснение и `evidence` с числами эталона. `network_summary` складывает эффекты отдельно по единицам. Взаимное влияние действий, бюджетные ограничения и двойной учёт совместных эффектов не моделируются, поэтому сумма — оценка резервов, а не гарантированный совместный результат.

## 11. Поиск аномалий

Код: [anomalies.py](backend/app/ml/anomalies.py), `detect` объединяет три детектора. Находки добавляются к результатам, но автоматически не исключают центр из кластеризации и рекомендаций.

### Логические правила

Получают `facts` и проверяют каждый центр:

- `0 < audience_total < supply_total` → `error`: меньше одного обученного на разработанный формат.
- При положительной аудитории `residents_total > 2 × audience_total` → `warning`: возможны разные контуры учёта.
- Продукты есть, аудитория равна 0 → `warning`.
- Услуги на положительную сумму при нулевых аудитории и продуктах → `warning`.

Эти условия указывают на возможную несогласованность. Например, разработанный формат не обязательно уже проведён, поэтому первое правило само по себе не доказывает опечатку.

### Робастная z-оценка через MAD

Получает натуральные показатели `profile`: аудиторию, предложение, участников на формат, продуктов на участника, услуг на участника и публичность на формат.

```text
median = медиана показателя по сети
MAD = медиана(abs(x − median))
z = 0.6745 × (x − median) / MAD
```

Если MAD нулевой, используется **среднее абсолютное отклонение от медианы**. Если оно тоже нулевое, все оценки равны 0. При `abs(z) >= 3.5` создаётся находка; при `abs(z) >= 7` уровень `warning`, иначе `info`. Единичные крайние значения меньше влияют на медиану, чем на обычное среднее.

### Isolation Forest

Вход — **11 преобразованных признаков `features.matrix` до StandardScaler и PCA**. Лес случайно выбирает признаки и пороги разбиения. Наблюдения, которые отделяются от остальных за меньшее число шагов, считаются более необычными.

Параметры: 300 деревьев, `contamination=0.15`, `random_state=42`. Доля 0,15 задаёт порог для необычной части обучающей выборки, а не обнаруженную долю ошибочных отчётов. Для метки `−1` создаётся `info` с `decision_function`; меньшая оценка соответствует большей необычности.

## 12. Агрегации и визуальные расчёты интерфейса

Не все вычисления проекта — машинное обучение. API `/overview` суммирует факты и эффекты, считает медианы, число статусов и аномалий. `/benchmark/{metric}` получает столбец `profile`, выдаёт медиану, квартили, минимум и максимум по сети, а также статистику групп. `/organizations/{id}` соединяет готовые результаты по `org_id`.

### Графики из API

- [SectionDynamics.vue](frontend-ml/src/components/SectionDynamics.vue): полосы состава аудитории — значения `audience_*` из `/api/organizations`, центры сортируются по общей аудитории. Кольцо форматов суммирует эти значения по сети. План-факт берёт `/api/plan`, исключает `без базы`, сортирует по выполнению.
- [SectionClusters.vue](frontend-ml/src/components/SectionClusters.vue): точки карты — `pc1` и `pc2` из `/api/clusters`. Это не t-SNE и не UMAP.
- [OrgModal.vue](frontend-ml/src/components/OrgModal.vue): выбирает центр, план, рекомендации и аномалии из уже загруженных массивов; диаграмма показывает аудиторию по форматам.
- Фильтры каталога и рекомендаций — сравнение строк, категорий и числовых порогов. «Высокая важность» — приоритет ≥ 80, средняя — ≥ 50, остальные — обычные. Это не отдельный классификатор.

### Радар групп: ручная шкала

В `SectionClusters.vue` рассчитываются средние абсолютные показатели членов выбранного кластера. Для каждой оси:

```text
балл = min(100, max(15, round(среднее / ориентир × 100)))
```

Ориентиры: аудитория 500; продукты 250; резиденты 400; услуги 2 500 000 ₽; публикации 80. Они заданы в коде. Сравнительная серия «Средняя норма сети» — константа `[50, 50, 50, 50, 50]`. Это не среднее сети, не PCA-признаки и не перцентили. Даже нулевое значение получает минимум 15 баллов.

В [theme.js](frontend-ml/src/theme.js) описания пяти архетипов привязаны к номерам 0–4 вручную. На изменённом датасете они могут разойтись с автоматически рассчитанным именем группы на бэкенде.

### Симулятор «Что если»

Код: [SectionRecommendations.vue](frontend-ml/src/components/SectionRecommendations.vue), `simulatedImpact`. Вход — суммы эффектов из `overview.recommendations.impact` и три ползунка.

```text
участники = round(baseParticipants × attendanceBoost / 20)
продукты  = round(baseProducts × conversionBoost / 15)
рубли     = round(baseRevenue × monetizeBoost / 10)
```

При исходных положениях 20/15/10 показываются базовые суммы эффектов. Это линейное масштабирование оценок резервов, не прирост от фактической аудитории на выбранный процент и не повторный запуск моделей. Нет моделирования стоимости, насыщения или взаимодействия действий.

При отсутствии **или нулевом значении** базы оператор `||` подставляет 1689 участников, 1411 продуктов и 9 669 800 ₽. Эти резервные числа заданы вручную.

### Динамика по кварталам: константы

`METRICS_CONFIG` в `SectionDynamics.vue` содержит готовые значения 2025 года, Q1, Q2, Q3, прогноза Q4, целей и подписей роста для четырёх метрик. Они не строятся из `overview` и не загружаются из временного ряда.

Например, аудитория задана как `3850 → 1150 → 2580 → 4193 → 5590`, цель — 5800. Подпись `+18.4%` также записана строкой и не пересчитывается из этих точек. Сглаживание линии средствами ECharts — только способ рисования, не прогнозная модель. Годовая база и накопленные квартальные значения дополнительно относятся к периодам разной длины.

### Отзывы, тональность, удовлетворённость и воронка

Код: [SectionFeedback.vue](frontend-ml/src/components/SectionFeedback.vue).

- Шесть исходных отзывов записаны в массиве `REVIEWS`. Имена, тексты, даты, оценки и тональность не приходят из Excel или API.
- Новый отзыв добавляется в локальный Vue `ref`: рейтинг ≥ 4 означает `positive`, ниже — `warning`. Текст не анализируется, NLP-модели нет. У исходных примеров тональность задана вручную и может не следовать этому правилу.
- Серверного сохранения и `localStorage` нет. При размонтировании раздела или перезагрузке новые отзывы теряются; они не участвуют в бэкенд-рекомендациях.
- Радар удовлетворённости использует константы `[4.8, 4.9, 4.6, 4.5, 3.9]` и `[4.2, 4.3, 4.0, 3.8, 4.2]`. Источника сравнения «вузы РФ» код не загружает.
- CSI/CSAT 84,6 %, удержание 94,9 %, конверсия 49,5 % и текст про 38 % критических отзывов заданы в шаблоне. Вычисления CSAT, NPS или retention по анкетам здесь нет. Число публикаций в отдельной карточке при этом берётся из `overview`.
- Воронка тоже задана вручную: 4193, 3981, 2074, 768; у «Федеральные показы: 78» числовое значение для размера — **350**. Форма графика не полностью отражает подписи.

В этой воронке смешаны люди, продукты и публикации, а связи конкретного человека с этапами нет. Деление продуктов на аудиторию не даёт долю людей, создавших работу; отношение резидентов к обученным не доказывает удержание одних и тех же людей.

### Текстовые выводы и отчёт

[SectionStory.vue](frontend-ml/src/components/SectionStory.vue) выбирает рекомендацию по продуктам с максимальным эффектом, первую ошибку и сводный резерв услуг. Текст формируется шаблонами. В описании первой ошибки числа 69 и 21 записаны непосредственно в компоненте; они не подставляются из выбранной аномалии. Формула «каждый N-й» использует обратное отношение продуктов к аудитории и не подтверждает индивидуальную конверсию.

[ExecutiveSummaryModal.vue](frontend-ml/src/components/ExecutiveSummaryModal.vue) отображает сводку и вызывает печать браузера. Печать/PDF не запускает новую аналитическую модель. Подпись «20 центров онлайн» в `App.vue` также задана статически, подключения к центрам в реальном времени нет.

## 13. Воспроизведение и проверка происхождения результата

Текущий `master`: [run.sh](run.sh) запускает API на **8010**, [vite.config.js](frontend-ml/vite.config.js) задаёт фронтенду **5180** и проксирует `/api` на 8010. У Vite не включён `strictPort`, поэтому при занятом порте фактический адрес нужно смотреть в строке `Local`.

Пересчитать аналитический слой без браузера:

```bash
cd backend
uv sync
uv run python - <<'PY'
from pathlib import Path
from pprint import pprint
from app.ml.pipeline import build_analytics, overview

a = build_analytics(Path('../DATASET'))
pprint(overview(a))
pprint(a.validation.as_dict())
pprint(a.recommendation_stability)
print(a.features.matrix)
PY
```

Этот расчёт не использует константы фронтенда. `validate=False` отключает дорогие проверки валидации, но не сам выбор `k` с оценкой устойчивости; результат валидации тогда содержит заглушку «валидация отключена».

При подготовке документа выполнен полный расчёт на `DATASET/`: 20 организаций, 26 исходных показателей, 11 признаков, 5 PCA-компонент, 5 кластеров, 50 рекомендаций и 17 аномалий. Силуэт — 0,3256; p-значение — 0,0005; средний ARI leave-one-out — 0,9824; доля устойчивых рекомендаций — 0,96. Расчёт занял около 11,8 секунды в текущем окружении. Это проверенный снимок результатов, а не обещание одинакового времени на другом компьютере.

Для числа из рекомендации смотри `evidence` и `scope`, затем исходную организацию и строку формы из раздела 3. Для изменения единиц или подстановки нуля — `/api/quality`. Для квартальной линии и оценок отзывов — соответствующие константы Vue, поскольку источника в Excel для них нет.

Случайные генераторы используют seed 42. Воспроизводить результаты нужно на тех же файлах, версии кода и зависимостях из lock-файлов. Число групп, эффект рекомендаций и время сборки в исходном README — результаты конкретного прогона, а не неизменяемые параметры алгоритма.
